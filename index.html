I’m most useful where a function is being built, or where an existing one needs to work better. A few examples, with an honest note on where each one stands.

  • Data pipelineA data foundation for a platform with no API Daily registration and roster data, flowing automatically into one base everyone can trust. +

    The problem

    The club’s registration platform has no API. Player, roster, and subscription data lived in manual exports, so every report depended on whoever had last downloaded a CSV.

    What I built

    A scheduled pipeline that pulls the daily exports into cloud storage and feeds an Airtable base of players, subscriptions, and team assignments. Records match on stable IDs and are updated or created, never deleted.

    Where it stands

    Collecting and cleaning the data is automated. The final write-back step is still in progress, and I’d rather say so than call it end-to-end.

    Google Cloud Run · Cloud Scheduler · Cloud Storage · Google Drive · Airtable · Zapier

  • CRM & lifecycleA lead-to-enrollment funnel One clear path from a family’s first question to a registered player. +

    The problem

    Families reached out through several channels, with no consistent way to qualify, route, or follow up on their questions.

    What I built

    A documented lead-to-enrollment workflow in HubSpot: intake, a qualification layer, territory-based routing to the right person, and follow-up sequences. Before building, I evaluated six CRMs and wrote the business case for the one we kept.

    Where it stands

    Automated from first inquiry through sales-qualified lead. Marking a family as a customer is still a manual step.

    HubSpot · Zapier

  • Staffing operationsFrom schedule PDFs to payroll-ready shifts Turning schedules in every shape into clean shifts, then catching the mismatches before payroll. +

    The problem

    Hourly coaches work across many facilities and programs, and schedules arrive as PDFs, grids, screenshots, and spreadsheets, each region in its own format.

    What I built

    A repeatable process that turns any schedule into shift imports: one row per coach per day, overlapping blocks merged, set-up time added, and game end times calculated from age-group game lengths. A pre-payroll report then flags missing clock-ins and large variances by region.

    An example

    One summer schedule became 500 per-person shift rows across 32 dates, which consolidated into 119 shared shifts. Each step has a check, so nothing gets silently dropped.

    Connecteam · Google Sheets · Python · Claude

  • Feedback loopsA weekend game-report system So directors know what happened at every game, and what needs a follow-up. +

    The problem

    There was no consistent way to learn what happened at weekend games, whether results were entered, or which concerns needed someone to follow up.

    What I built

    Every Friday, a sync rebuilds one list of fixtures from every league we play in. Coaches pick their game from a simple form and file one report. Directors get a prioritized follow-up queue, serious incidents at the top, and can nudge everyone who hasn’t filed with one click.

    Why it’s built this way

    It runs on Google Sheets because that’s where staff already work. Safeguards keep reports attached when games are rescheduled and refuse a sync if a league’s data suddenly drops.

    Google Sheets · Apps Script · Zapier · ClickUp

AI in operations

Useful, not magic

Most of my AI work isn’t glamorous. It takes a recurring, messy input and turns it into a clean, checked output, so people can spend their time on players and families instead of spreadsheets. These run as saved, reusable workflows.

  • League schedule importLeague export → registration-platform import file, plus a punch list of team names that need a human
  • Season schedule exportA league website with no download button → a full-season workbook of about 475 games, with a refresh mode
  • Coach shift importSchedule PDFs, grids, and screenshots → shift import file, merged and padded
  • Pre-payroll exception reportTimesheet export → missing clock-ins and large variances, by region
  • Registration follow-up trackerProgram exports → who has and hasn’t registered, by team, with a follow-up list
  • Process documentationA rough outline → a standardized process document, filed where people can find it
  • Camp family recapThe day’s notes → a draft family email and social post, reviewed before anything goes out
  • Inbox themesA full inbox export → the questions families actually ask most, grouped by theme

Guardrails I build in

  • Drafts only. Nothing goes to families automatically.
  • Never overwrite a person’s edits.
  • Flag conflicts instead of quietly resolving them.
  • Verification checks on every import.
  • Limit what personal data an AI tool can see.
  • Write the process down, so it outlives the person who built it.

How I work

  • Systems first, then the tool

    Understand how the work actually flows and who owns what, then choose software that fits. Not the other way around.

  • Meet people where they work

    Put the form in the app coaches already open. Use the platform families already have. Adoption is the real test of a system.

  • Show the math

    If a number can’t be traced back to its source, it isn’t ready to make decisions with.

  • Don’t let perfect block useful

    Design a manual fallback so something helpful ships now, while the fuller version gets built.

  • Be honest about status

    “Automated through step four, manual after that” is more useful than “fully automated.”

  • Pilot, then scale

    Start with one team or one region, learn what breaks, and earn the right to roll it out.
