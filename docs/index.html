  • Data pipelineA data foundation for a platform with no API Unlocking registration data so reporting and internal tools have one source of truth. +

    The problem

    Every report and internal tool needed data that was locked inside the club’s registration platform, which has no API or MCP connection. Player, roster, and subscription data lived in manual exports, so every number depended on whoever had last downloaded a CSV.

    What I built

    A pipeline that moves scheduled exports into cloud storage and feeds an Airtable base, which serves as the club’s data layer. Records match on stable IDs, so each update lands on the right player and nothing is duplicated or lost.

    The result

    One trusted source for the data the club runs on. New reports, dashboards, and internal apps build on top of it, instead of each one starting from another spreadsheet.

    Google Cloud Run · Cloud Scheduler · Cloud Storage · Google Drive · Airtable · Zapier

  • CRM & lifecycleA lead-to-enrollment funnel Every interested family gets a prompt response and a clear path to registering. +

    The problem

    Families reached out through several channels, with no consistent way to qualify them, route them, log the conversation, or follow up. In peak season, inquiries outpaced what the team could handle, so good leads were missed and went cold.

    What I built

    A documented lead-to-enrollment workflow in HubSpot: intake, a qualification layer, routing by region, and follow-up sequences triggered by each prospect’s digital signals. Before building, I evaluated six CRMs and wrote the business case for the one we kept.

    The result

    Every prospect is contacted promptly, then gets timely touchpoints that help qualify and convert them. Conversion rates went up, and families move from first question to registered faster.

    HubSpot · Zapier

  • Staffing operationsFrom schedule PDFs to payroll-ready shifts Schedules in any format become accurate shifts in a fraction of the time. +

    The problem

    Entering hourly staff schedules into the club’s scheduling platform by hand took a lot of time. Schedules arrived as screenshots, PDFs, and spreadsheets, and retyping them invited mistakes that could follow through to payroll.

    What I built

    A repeatable process that turns a schedule in any format into a shift import, building accurate shifts automatically from the rules for each type of job. Before payroll, a report flags differences between scheduled and worked hours so they get fixed first.

    The result

    Schedule entry takes a small fraction of the time it used to, and it’s more accurate, with fewer errors reaching payroll.

    Connecteam · Google Sheets · Python · Claude

  • Feedback loopsA weekend game-report system Directors know what happened at every game, and what needs a follow-up. +

    The problem

    Directors had no consistent way to hear from coaches about weekend games: what happened, whether results were entered, and which concerns needed a follow-up. Getting answers meant a lot of time-consuming back-and-forth.

    What I built

    A weekly sync that builds one list of fixtures from every league we play in. Coaches pick their game from a simple form and file one report. Directors get a prioritized follow-up queue, with serious incidents at the top, and can nudge everyone who hasn’t filed with one click.

    The result

    Directors save hours they used to spend chasing updates. Issues surface and get addressed sooner, which means a better experience for players and families.

    Google Sheets · Apps Script · Zapier · ClickUp

  • ReportingA dashboard that can show its math Year-over-year registration pacing that leadership can rely on. +

    The problem

    Leadership relies on a registration pacing dashboard to see whether we’re ahead of or behind last year. But you had to understand the data underneath it to trust what it was saying.

    What I built

    A rebuild that compares rostered players by program, region, gender, and age group against the same date last year, with a parallel spreadsheet model that shows the work. Closed seasons are archived, so a refresh never erases history.

    The result

    A management reporting tool people can rely on. The data feeding it is transparent, so when something looks off, the cause is quick to find.

The Select Playbook

63 plays · 6 areas · 10 run as skills

Most of what keeps a club running lives in a few people’s heads. The Playbook writes it down, one repeatable “play” at a time, so the work doesn’t depend on who happens to be available.

The problem

Most of the club’s repeatable processes lived in one or two people’s heads. Getting something done often meant finding the right person to ask.

What I built

An operations playbook of 63 plays across six areas: registration, scheduling, staffing, data, marketing, and leadership. Every play follows the same structure, and ten of them run as saved AI skills, so the documentation and the automation are the same thing.

The result

Knowledge that outlives any one person. Anyone can see how a process works, who owns it, and what starts it, and the most repetitive plays are already automated.

AI in operations

Useful, not magic

Most of my AI work isn’t glamorous. It takes a recurring, messy input and turns it into a clean, checked output, so people can spend their time on players and families instead of spreadsheets.

How the club’s Claude workspace is set up

I set up and configured the club’s Claude Team account around a few deliberate decisions:

  • A written AI use policy

    We agreed on the rules first: only aggregated or pseudonymous player data, read-only lookups through connectors, and drafts that a person reviews before anything is sent.

  • Connected to where work happens

    Connectors to Google Workspace, HubSpot, ClickUp, Notion, and meeting notes, plus Zapier for other apps, so answers come from the club’s real systems instead of copy and paste.

  • Shared skills for recurring work

    Repeatable tasks are saved as skills anyone on the team can run, so the same job gets done the same way every time.

  • Built to grow the Playbook

    Claude is set up to watch for repeatable systems and suggest them as Playbook candidates, so documentation happens during the work, not after it.

  • An AI fluency rubric

    A rubric across six club roles that describes what good AI use looks like in each one, so people know what to aim for.

  • Leadership and admin first

    Access started with leadership and admin roles, so we could learn what works before widening it.

Everyday automations

These run as saved, reusable skills.

  • League schedule importLeague export → registration-platform import file, plus a punch list of team names that need a human
  • Season schedule exportA league website with no download button → a full-season workbook of about 475 games, with a refresh mode
  • Coach shift importSchedule PDFs, grids, and screenshots → shift import file, merged and padded
  • Pre-payroll exception reportTimesheet export → missing clock-ins and large variances, by region
  • Registration follow-up trackerProgram exports → who has and hasn’t registered, by team, with a follow-up list
  • Process documentationA rough outline → a standardized process document, filed where people can find it
  • Camp family recapThe day’s notes → a draft family email and social post, reviewed before anything goes out
  • Inbox themesA full inbox export → the questions families actually ask most, grouped by theme

Guardrails I build in

  • Drafts only. Nothing goes to families automatically.
  • Never overwrite a person’s edits.
  • Flag conflicts instead of quietly resolving them.
  • Verification checks on every import.
  • Limit what personal data an AI tool can see.
  • Write the process down, so it outlives the person who built it.

How I work

  • Systems first, then the tool

    Understand how the work actually flows and who owns what, then choose software that fits. Not the other way around.

  • Meet people where they work

    Put the form in the app coaches already open. Use the platform families already have. Adoption is the real test of a system.

  • Show the math

    If a number can’t be traced back to its source, it isn’t ready to make decisions with.

  • Don’t let perfect block useful

    Design a manual fallback so something helpful ships now, while the fuller version gets built.

  • Be honest about status

    “Automated through step four, manual after that” is more useful than “fully automated.”

  • Pilot, then scale

    Start with one team or one region, learn what breaks, and earn the right to roll it out.
